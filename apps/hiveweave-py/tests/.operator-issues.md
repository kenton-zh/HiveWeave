## 详细记录（按时间排序）

### 1. 前后端联调时序（18:26 · 设计问题）

- **现象**：后端 A047 已完成+提交+自测（8080/health ok、API CRUD 可用、持久化重启验证过），但前端 A048 的 `frontend/` 未提交，后端 mount frontend/ 目录不存在 → GET / 返回 404。
- **介入/处置**：未介入，仅观察记录。属正常并行开发中间态。
- **根因假设**：后端先做完启动自测时前端还没交付，契约是最终一起交付，中间态后端单独跑会 404。
- **复盘建议**：不算真 bug，是并行开发的正常中间态。终验要求前后端一起交付即可覆盖。

### 2. 任务进度与产出不同步（18:26 · 设计问题·疑似）

- **现象**：任务长时间停在 claimed progress 10，但 worktree 里后端代码已提交（797ff6d）、已自测。任务进度与 worktree 实际产出不同步。
- **介入/处置**：未介入，观察中。后续后端任务自然流转到 submitted(90)，说明只是提交前的正常延迟，非卡点。
- **根因假设**：开发中→提交任务需要时间，进度更新有滞后。
- **复盘建议**：不是 bug。但任务进度（prog 10）与实际产出（代码+自测完成）不同步，容易误导观察者。

### 3. worktree 隔离 vs 跨端协作（18:31 · 设计问题）

- **现象**：前端 A048 开发时需对齐后端 API，但自己的 worktree 只有 README，看不到后端实际代码，只能 "check the backend owner's worktree to align the API"。
- **介入/处置**：未介入，仅观察记录。A048 靠契约文档 + 跨 worktree 偷看解决。
- **根因假设**：worktree 按 owner 隔离文件，但前后端联调时前端需要看到后端真实接口实现。契约文档（`.hiveweave/shared/taskflow-contract.md`）是关键桥梁。
- **复盘建议**：契约文档机制是否足够？是否需要更强的接口 mock/共享。目前契约定稿后前后端对齐良好，说明契约文档有效。

### 4. QA 终验质量高（18:41 · 正面观察）

- **现象**：QA 海盐终验执行认真：run.sh 启动 8080、curl CRUD、DB 插 PERSIST-PROBE 后重启验证持久化、真实浏览器打开看板确认 2 张卡片渲染+截图。
- **介入/处置**：无需介入。
- **复盘建议**：QA 行为可作为正面样本。

### 5. 验收证据基线过期返工（18:44 · 设计问题）

- **现象**：QA 提交 VERIFY 后端（62164ddc），review 被退回（review_rework），理由 "attestation 基于 797ff6d，但 main tip 已是 8992c22（前端合并）"。
- **介入/处置**：未介入，仅观察记录。
- **根因假设**：验收门要求证据 commit == main tip。但 797ff6d→8992c22 的 diff 只动了 frontend/，与后端 VERIFY 范围无关，仍要求重做。
- **复盘建议**：基线校验是否应按 "diff 是否触及验收范围" 判断，而非简单比较 tip？纯增量（不相关目录）不应触发返工。当前逻辑偏保守，增加无效工作量。

### 6. 并发验收共享运行时互相干扰（18:52 · 设计问题）

- **现象**：QA 发现 DB 里出现别人（潮汐）的 E2E 痕迹数据（id=2 "survives restart"），与自己的探针（id=1/id=4）冲突——多人同时对一个 8080 服务 + 同一 taskflow.db 做验收。
- **介入/处置**：未介入，仅观察记录。
- **根因假设**：worktree 只隔离代码，不隔离运行时。多个 agent 同时跑验收会共用端口/DB 文件，数据互相污染。
- **复盘建议**：是否需要给验收类任务提供独立运行时沙箱（独立端口 + 独立 DB 副本）？或约定验收串行化。当前靠 agent 自己识别 "是别人的痕迹" 绕开，靠自觉不够稳。

### 7. 审批链权责分离生效（18:55 · 正面观察）

- **现象**：潮汐作为前端合并者主动声明 "不能审其 VERIFY"，转交 CEO 统一 approve；CEO 审查发现 attestation 基线过期打回重做（review_rework）。
- **介入/处置**：无需介入。
- **复盘建议**：平台治理规则（合并者不能审、证据基线校验）被真实执行，治理设计有效的正面证据。

### 8. CEO 被 ARK 400 砖化（19:05 · 程序 bug·P0）

- **现象**：CEO 归零（A044）被 ARK 400 死循环砖化：t19 轮流式中断（stall_break）时 ask_agent 的 tool_call arguments 被截断成非法 JSON 并持久化，后续每次请求都携带该历史 → 网关校验请求体 400「Invalid request body」→ consecutive_errors=7，两个 VERIFY 审批卡死。
- **介入/处置**：**已修复**。`_clean_messages` 增加读时净化 `_sanitize_tool_call_arguments`——非法 arguments 就地替换为合法占位 JSON（保留 preview）。新增 `test_clean_messages_sanitize.py` 7 测试全过。重启后端加载。
- **根因假设**：流式 stall 时截断的 tool_calls 原样持久化；执行期容错（产生 Parameter error 回执）但读侧未净化。
- **复盘建议**：修复已上。复盘可加写侧防线：stall finalize 时不持久化不完整 tool_call。ARK 会校验 arguments 合法性，其他网关不一定——属隐性依赖。
