2. P0 — 致命死锁（平台级 BUG）

P0-1VERIFY 审批门禁在小团队必然死锁，只能取消绕过

现象
云雀完成 VERIFY 并提交后，没有任何人能 approve：
  • CEO（归零）approve 被拒 —— 系统是 CEO merge 的父任务，evidence.merged_by 命中「合并人不得自批」；
  • 潮汐 review 被拒 —— 父任务 implementer；
  • 团队共 3 个可审角色，全部出局。归档原文：「VERIFY 任务被 approval gate 阻塞：CEO 因 merge 父任务被拒，潮汐（implementer）也被拒，全团队无独立 reviewer」。
根因（设计自相矛盾）
规则 A：「VERIFY 的 creator 落 CEO（审权不落回 merger）」。规则 B：「VERIFY 禁 merger 自批」。 当 merger 恰好是 CEO 本人时（小团队 CEO 亲自动手 merge 是常态），A、B 直接冲突，审批空集。 平台有 merge_proxy（merger 失联兜底）和 retry_qa_blocked_verify_tasks（QA 缺席兜底）， 唯独没有「reviewer 缺席」兜底。门禁把所有人都挡在外面后，系统层面唯一出路就是 CEO 手工取消 —— VERIFY 机制形同虚设。
解决方案（按优先级）：
  1. human gate 兜底：沿 parent 链找不到合法 reviewer 时，verification_case 进入 reviewer_absent 状态并自动 message_user 升级给用户一键 approve/waive（复用 merge_proxy 的祖先链逻辑，链顶无人时落 human）。
  2. 小团队降级策略：active 协调者 ≤ 2 时允许 CEO approve，evidence 标注 override: no_independent_reviewer，审计可追溯。
  3. 根治：merge 与 approve 解耦 —— CEO merge 后 VERIFY 的 reviewer 默认落「下一个被 hire 的 QA/审查员」，而非要求当场存在。

P0-2任务「转发」无系统语义 —— 当下正在进行的三方死锁

现象（数据库当前状态）
tasks.d5e102bb: status=running, progress=20, assignee=潮汐(implementer) 潮汐 agent_waits: "等待云雀完成 attest_doc_review 并 submit_task" (expires 20:55:59) 云雀 work_log: "无待办。VERIFY 0005ab65 已完成归档。task d5e102bb 非我 assignee" 奥丁 agent_waits: "等待归零 dispatch → 云雀执行并 submit" (认知与事实不符)
根因
CEO 的意图是「云雀执行、奥丁审」，但任务系统里 assignee 只能是潮汐（CEO 派工硬门：assignee 只能是直属中层）。 「转发给云雀」只存在于自然语言指令里 —— 平台没有 delegate/forward 语义，消息里带 task_id 不产生任何义务。 云雀的 obligation 账本里没有这个任务，正确判断「非我 assignee，无待办」后合法 idle。 三个 agent 各自行为都「合规」，合成结果却是永久死锁。stall 看门狗 10 分钟后会举红框，但红框不解死锁。
解决方案：
  1. 立即处置（现在就能做）：CEO 执行 cancel_task(d5e102bb) → 重建 VERIFY，assignee=云雀, reviewer=奥丁；或平台提供 transfer_task 把 assignee 改为云雀。
  2. 工具补齐：新增 delegate_task(task_id, executor_id) —— assignee（问责）不变，显式登记执行人，executor 的 obligation 账本同步入账。
  3. 平台护栏：检测到「消息引用 task_id 但接收方非 assignee/executor 且无义务」时，回执警告 sender「对方账本无此任务，不会行动」；消息引用活跃 task_id 时强制 wake=1。
  4. VERIFY 任务结构化：spawn VERIFY 时直接支持 executor_id + reviewer_id 双字段，不再靠 prompt 路由。

3. P1 — 平台设计缺陷（规则互相打架）

P1-1attestation gate × WORKTREE PIN 冲突，逼 CEO 主动违规

证据链
潮汐 turn_result: "submit 被 attestation gate 拦住（文件在 worktree 不在 main），已发消息给归零请示方案" 归零 turn_result: "已回复潮汐同意方案1：临时写specs/checkin.md到项目根目录用于attestation" tool_attestations: 全部 4 条 workspace = "D:\PC_AI\Project\TEST13"（项目根，非 worktree）
docs_only 任务强制 attest_doc_review，但 attestation 只认项目根/main 的文件； WORKTREE PIN 又硬性禁止写项目根。两条硬规则把合规路径封死，CEO 只能指示下属破坏 PIN。 这是本次事故链的第一张多米诺骨牌 —— 后面 main dirty、auto-save、审计断裂全部由它引发。
解决方案：
  1. attest_doc_review 支持 workspace="worktree" 参数：在提交者自己的 worktree 内取证，artifact_hashes 记录 worktree 相对路径 + 分支名 + commit。
  2. docs_only 提交契约改为两段式：worktree 内 attest（提交时）+ main 上复核（VERIFY 时），两段都用 attestation，不再出现「必须写 main 才能 attest」的窗口。

P1-2worktree 分支零提交，merge 审计链断裂

证据
git log --all: 仅 3 个 commit，全部在 main 2a50a36 initial (仅 .gitignore) 92f4fea pre-merge-checkpoint: auto-save dirty main ← spec 由此进入 main 44afce8 pre-merge-checkpoint ← 空提交 hw/A003/work 指向 44afce8 —— 从未有过独立提交
项目唯一产出未经任何 agent 分支，通过「dirty main 自动存档」兜底进入 main。 git_worktree_merge 对「零提交分支」不警告不拒绝，no-op merge 照样成功。 CLAUDE.md 规定的审查口径「审代码读 worktree」在本项目完全落空 —— worktree 里根本没有可审的提交。
解决方案：
  1. merge 前校验分支 ahead count：== 0 时拒绝 merge，提示「分支无提交，请先在 worktree 内 commit」。
  2. submit_task 时校验 evidence.files_changed 与 worktree 分支 diff 一致，不一致拒收。
  3. auto-save dirty main 触发即广播 agent_health=error / lobby 告警 —— 这是异常路径，不该静默兜底。

P1-3VERIFY 取消后 verification_cases 永久悬挂

证据
verification_cases: status=in_review, closed_at=NULL (verify_task_id=0005ab65 已 cancelled, merge_commit=44afce8) 归零 work_log: "VERIFY 任务取消后，父任务已转为 approved。但 verification_case 仍 in_review。需要用户决策。"
任务被取消，关联的 verification_case 没有级联关闭，成为孤儿记录。CEO 自己发现了不一致， 但平台没有任何工具让它修复 —— 只能「留给用户决策」。状态机出现系统自己都感知却治不了的脏数据。
解决方案：
  1. cancel_task 级联：取消 VERIFY 任务时同步关闭关联 verification_case（status=cancelled, closed_at, reason）。
  2. 启动对账（reconcile）增加一项：scan「任务已终态但 verification_case 未关闭」的记录并修复。
  3. 父任务状态回退（verifying→approved）应写 task_event 说明原因（当前 payload 为空，审计断点）。

4. P2 / P3 — 效率与一致性问题

P2-1已通过的验证结果作废，无复用机制

云雀对 0005ab65 的 attestation（835e5bfe）至今有效 —— artifact hash 与 main 上文件完全一致。 VERIFY 被取消重建后，平台要求从头再做一遍，同一 merge_commit 下已通过的 attestation 无法被引用复用。
解决方案：重建 VERIFY 时检测同 merge_commit_hash 的已通过 attestation，evidence 允许 reuse_attestation_ids，reviewer 确认后直接 approve。

P2-2关键执行指令以 wake=0 / expect_report=0 发出

潮汐 → 云雀 inbox: task_id=d5e102bb, wake=0, expect_report=0 （内容为 VERIFY 执行指令 —— 对方不被唤醒、不被要求回复）
云雀若不是被其他事件恰好唤醒，根本看不到这条指令。指令类消息靠运气投递。
解决方案：消息携带活跃 task_id 且内容含执行指令时，平台强制 wake=1；或至少在 send 回执中提示「对方不会被唤醒，确认？」。

P2-3CRLF/LF 不一致，artifact hash 跨环境不可复现

main 根 specs/checkin.md: LF sha256=5e533600… worktree A003/A005 同文件: CRLF sha256=e3af9759… （git autocrlf 检出转换所致；attestation 记录的是 main 版本 hash）
同一份文档两个 hash，attestation 的 artifact_hashes 在不同 checkout 环境下无法比对验证。
解决方案：仓库根加 .gitattributes（*.md text eol=lf）；attestation 计算 hash 前统一规范化换行符。

P3-1CEO waiting 泛滥 + agent 间事实认知漂移

15 条 agent_waits 中 CEO 占 11 条，曾在 3 秒内连续两次 ask_agent 催潮汐（20:36:36 / 20:36:39）， 大量 WAIT_WITHOUT_ASK soft pass。另外奥丁被告知的任务事实（assignee=云雀）与 DB 实际（assignee=潮汐）不符 — 事实靠 CEO 手打自然语言传递，必然漂移。
解决方案：
  1. 同 ref 同 note 的 wait 自动合并去重；ask 发出后重置 wait 计时而非叠加新 wait。
  2. dispatch/交接消息由系统自动附加结构化事实块（task_id / assignee / status / reviewer），agent 不可改写。

5. specs/checkin.md 文档自身缺陷（唯一交付物）

SPEC-1§5.4 连续打卡规则自相矛盾（实现者会无所适从）

原文：「如果今天未打卡，连续天数为 0（除非今天尚未打卡但昨天已打卡… 规则：连续打卡从最近一次打卡开始算，中间不可断）」
「为 0」与括号里的「除非」直接冲突；F5/F6/F7 三个验收用例又给出第三种解读。 核心歧义：今早打开页面（今天还没打），streak 显示 0 还是显示截至昨天的连续天数？ 按 §5.4 前半句是 0，按括号例外是昨天的值，按 F7 是「从最近一次延续」。
解决方案：建议明确为「今天未打卡时显示 frozen streak（截至昨天的连续天数），今日打卡后 +1」，并同步改写 F6 的预期（昨天未打卡 → 显示 0，因为 frozen streak 截至昨天已是 0）。

SPEC-2缺多标签页并发场景

B4 只防单页快速连点。两个标签页同时打开时，A 页打卡后 B 页按钮仍可点、可重复写入 —— localStorage 无跨标签锁。
解决方案：监听 storage 事件同步打卡状态；或打卡前重读 localStorage 做最终判定，而不是只用内存状态。

SPEC-3日期时区未定义

date: "YYYY-MM-DD" 按设备本地时区还是 UTC？跨时区旅行、夏令时切换时会打错卡或断连续。
解决方案：spec 写明「按设备本地时区取日界」，demo 阶段可接受；正式版建议固定业务时区。

SPEC-4B3 午夜跨天方案与 F4 不一致

F4 要求「打开页面即显示今天」，B3 对已打开页面跨天却只「提示用户刷新」——同一场景两种自动化标准。
解决方案：每分钟日期检查命中跨天时自动重置今日打卡状态（重读记录、解锁按钮、shift 7 天格子），toast 仅作告知，不要求用户手动刷新。
