二、BUG 清单(按严重度排序)

P0BUG-1:UNREPLIED_ASKS 软放行 → 回复契约失效 → 组织级死锁

现象:agent 收到 expect_report=1 的 ask,只用文字作答、不调 send_message,也能 done_slice 收工;提问方空等到超时。

机制(四个环节环环相扣,缺一都不会死锁):

  • ① turn_tools.py:146 预检命中后交 classify_commit_gate_soft_warn 判定——所有门禁码首次犯规一律软放行(接受 TurnResult + end_turn=True),注释写明动机是「减少浪费的 LLM 往返」;
  • ② 软放行回执同时说「Do NOT call any more tools」和「Same gate will HARD REJECT on repeat」——两句自相矛盾:工具循环已终止,agent 本回合不可能再犯第二次;clear_pending_turn_result 在新回合清空计数。hard-reject 路径是实际死代码,永不触发;
  • ③ turn_session.py:63 软放行码记入 _soft_passed → turn_exit.py:391 filter_soft_passed_violations 把它从兜底检查里剔除——权威兜底 evaluate_turn_exit 被自己的预检压制(日志 turn_exit_ok disposition=complete 实证);
  • ④ agent.py:1643 的逃逸阀 _ESCAPE_VALVE_THRESHOLD=5 只在兜底看到未回复时累计——软放行绕过兜底,逃逸阀同样永不生效。

与文档的矛盾:CLAUDE.md 写明「未回 ask → 拦截并续跑(最多 3 次)」,实际行为是「首次直接放行」。文档承诺的是硬门,代码实现的是软门。

修复(P0a,改一处即可止血):在 turn_tools.py 预检处理中把 UNREPLIED_ASKS 列入硬门集合(如 HARD_GATE_CODES = {"UNREPLIED_ASKS"}),绕过 soft-warn 分类,直接走现有的 ToolResult.err("commit_turn REJECTED (synchronous gate)…请先处理这些义务再 commit_turn") 分支——该分支返回错误不终止回合,LLM 会在本轮 tool loop 内补发 send_message 再重新 commit,正好多花的那一次 LLM 往返就是契约的代价。
修复(P0b,语义自洽):soft-pass 的设计对「提醒类」违规(WAIT_WITHOUT_ASK 修好后)可保留,但回执文案必须改:删掉不可达的「HARD REJECT on repeat」承诺;且 soft-pass 不应记入 _soft_passed 去压制兜底——兜底应对同一违规保留一次「拦截续跑」权(与 CLAUDE.md 的 3 次承诺对齐)。

P0BUG-2:WAIT_WITHOUT_ASK 预检对花名 ref 100% 误报(告警疲劳)

现象:本次运行 6 次 phase=waiting 提交,6 次全部命中 WAIT_WITHOUT_ASK 软警告——其中至少 5 次 agent 确实已在同回合给对方发过消息/ask。

机制:turn_exit.py:570 预检调用 _ref_in_set(ref, evidence, {}):

  • evidence 来自 get_sent_recipients_since,是 UUID 集合(如 4c6cbb1e-…);
  • agent 的 waiting_on.ref 是花名(「天线」「云岫」,来自注入的精简通讯录);
  • _ref_in_set 的花名解析依赖第三个参数 name_by_id——预检硬编码传了空 dict {};前缀匹配要求 len(ref) ≥ 4,两字花名直接跳过。

三层全灭 → 必假阳性。而兜底侧(agent.py:1625-1639)明确做了「Enrich messaged_refs with display names」,不缺正确实现,只是预检没复用。

后果:每次 commit 都带一条假警告,真违规(BUG-1 那次)淹没在噪音里——告警疲劳直接削弱软警告通道的存在意义。

修复:① pre_check_exit_gates 里按 evidence 中的 UUID 查 agents 表构建 name_by_id(同时收录 short_id,如 A003),传给 _ref_in_set;或更省事——与 backstop 对齐,预检直接把 evidence 集合 enrich 成「UUID + 花名 + short_id」三形态。② 回归测试三例:ref=花名 / ref=short_id / ref=UUID 前 8 位,各发一条消息后 commit waiting,断言无误报。

P1BUG-3:预检与兜底「未回复」判定口径不一致

机制:预检(turn_exit.py:577)用 expect_report=1 AND read=0 —— 消息一旦被标读,已读≠已回复,预检永远不再触发;兜底用 turn 级 collect_unreplied_asks(本回合处理的消息 + 送达证据 + 合约关闭)。两套口径独立演化:预检可能漏报(已读未回),也可能与兜底结论冲突。

修复:预检改用与兜底同源的「未关闭 reply_contract」口径(get_outstanding_ask_recipients 已有现成实现,方向反过来用),或直接让预检复用 collect_unreplied_asks(传入本回合 pending_msgs)。一个契约,一个判定函数,两处调用。

P1BUG-4:契约泄漏后没有任何恢复通道

机制:周期性 stall/unreplied 催办按设计禁用;推进依赖 agent.turn.after 的 task-advance hook——但 agent 已 complete 不再运行,没有 turn 就没有 after(日志实证:self_retrigger_complete_skip)。CEO 的 wait 要等 16.5 分钟超时,且超时唤醒不携带「对方始终未回复」的结构化状态;云岫那份 M1–M5 拆解永远锁在它自己的聊天记录里,CEO 不可见。

修复:① wait 超时唤醒的 digest 附带结构化字段:{"wait_ref": "云岫", "ask_outstanding": true, "ref_last_active": ...},让被唤醒方知道「等的东西没来」,而不是空醒;② 超时同时向欠债方重发一条 reply_required nudge(ask 重发,非文案猜测,用的是既有合约字段);③ 可选:game_time tick 扫「expect_report=1 且合约 N 分钟未关闭且目标 idle」的记录,作为 P0a 失效时的最后防线。

三、设计问题(非崩溃级,但持续放血)

P2D-1:组织不变式只能靠「试错」发现,且与「别膨胀」诉求冲突

「executor 不得挂 CEO」是硬不变式,但 HR 的招聘技能/系统提示里没有前置说明——只能靠 hire 失败 → 反问 CEO → 再 hire 的试错链发现,本次多花约 2 分钟并触发一次 WAIT_CYCLE 死锁。同时用户明确说了「少量中层/执行者即可,别膨胀」,而 1 人 demo 被迫建成 4 agent 三层组织;project_meta 里 orgPattern: "solo" 与自动创建 CEO+HR+全组织的实际行为也名实不符(值得确认 solo 的语义)。

建议:① 把 org 不变式(executor 不挂 CEO、直属 ≤7、岗位唯一等)直接写进 HR 与 CEO 的系统提示——机械规则不该靠工具报错传授;② HR 命中该错误时自动插入 coordinator 并 notify CEO 即可,无需请示(错误信息本身已给出唯一合法解);③ 评估 solo/微项目是否允许 executor 直挂 CEO(显式 override 参数),消除小项目强制三层。

P2D-2:协议可靠性的重担正被转嫁给 prompt

用户给 CEO 的原始指令里带了 6 条「硬规则」(docs_only、reassign_task、approve 后必须 merge、不要用纯文字指望产生义务……)——全部是平台该用结构化门禁保证的事,现在靠用户手写 prompt 打补丁。本次事故正是第 4 条预言的应验。prompt 是建议,门禁才是协议;凡是被用户写进指令补丁的平台行为,都应视为平台缺陷登记在案。

P2D-3:小观察项

  • 21:22:47 日志出现对 A003 的 org.update_agent fields=["worktree_error"] 写入,随后 worktree_heal_tick 报 recovered=0/failed=0,而磁盘上 worktree 实际存在——建议顺手确认这次写入的内容(是清空还是误报错误)。
  • 潮汐(A004)worktree 与分支在 hire 时创建,整个生命周期 0 次运行——招聘即建树的成本在「招而不用」场景下是纯浪费,可考虑懒创建(首次有写任务时建)。
